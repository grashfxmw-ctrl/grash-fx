# Financial rules and lifecycle

## Proposed plan data

| Plan | Proposed daily rate | Minimum | Term |
|---|---:|---:|---:|
| Starter | 10% | $50 | 7 days |
| Basic | 20% | $500 | 7 days |
| Premium | 30% | $1,000 | 7 days |
| VIP | 40% | $2,000 | 7 days |

These rates were supplied as business requirements but are not independently validated. They are stored as inactive drafts. They must not be represented as guaranteed returns.

## Rate calculation

The initial schema records a rate basis of `simple_daily`. Under simple daily arithmetic, if a rate is approved and an investment principal is P, the illustrative seven-day profit would be:

`profit = round_to_currency_minor_unit(P × daily_rate × 7)`

This is only a calculation rule, not a claim that the profit will be earned or payable. Compounding, fees, taxes, losses, eligibility and the actual operating model must be explicitly resolved before activation. Do not calculate authoritative profit in browser code.

## Lifecycle

1. Client submits an investment request with a unique idempotency key.
2. Server checks verified/active account, approved active plan version, currency, minimum and available ledger funds.
3. In one database transaction, debit the principal from the client's available ledger balance and create an investment using a snapshot of the approved plan terms.
4. The start and maturity timestamps are generated by the server. For a seven-day term, maturity is the start timestamp plus seven days.
5. A scheduled server worker finds due active investments, locks each row, checks maturity, and writes eligible principal/profit credits once. The worker then marks the investment matured in the same transaction.
6. On error, roll back and retry safely; alert staff for repeated failures.
7. A withdrawal request may use only eligible available ledger funds. Staff separately verify and record the external payment.

## Ledger invariants

- Ledger entries are append-only.
- Amounts use exact decimal values and an explicit currency.
- A debit is negative; a credit is positive.
- Every entry has a unique idempotency key and an auditable source.
- Never silently edit history; corrections use linked reversal/correction entries.
- Website ledger totals do not prove that external funds exist.
- Reconcile the ledger against external bank/payment records every day.

## Not implemented yet

The schema does not itself implement account authentication, row-level security, available-balance checks, investment creation, deposit confirmation, withdrawal payout, maturity worker scheduling, notifications or payment integrations. These require provider-specific server-side code and tests.
